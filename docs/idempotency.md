# 멱등성과 Idempotency-Key 학습 노트

## 1. 멱등성이란

멱등성은 같은 요청을 한 번 보내든 여러 번 보내든 서버의 최종 상태가 같아야 한다는 성질이다.

예를 들어 `DELETE /cart/items/1` 요청은 처음에는 장바구니 상품을 삭제하고, 이후 같은 요청은 이미 삭제된 상태를 다시 확인하는 정도로 끝낼 수 있다. 최종 상태는 계속 "상품이 삭제됨"이므로 멱등적으로 설계할 수 있다.

반대로 `POST /orders` 요청은 같은 요청을 여러 번 보내면 주문이 여러 개 생성될 수 있다. 이런 API는 기본적으로 멱등하지 않다.

## 2. 왜 문제가 되는가

중복 요청은 사용자가 악의적으로 보낼 때만 생기지 않는다. 실무에서는 정상적인 사용 흐름에서도 쉽게 발생한다.

- 사용자가 주문 또는 결제 버튼을 빠르게 여러 번 클릭한다.
- 프론트엔드가 타임아웃을 보고 같은 요청을 재시도한다.
- 모바일 네트워크가 불안정해서 사용자는 실패로 보지만 서버는 이미 처리했다.
- 백엔드가 외부 API 호출 후 응답을 받지 못해 같은 작업을 다시 시도한다.
- 메시지 큐 소비자가 같은 메시지를 두 번 처리한다.

특히 주문, 결제, 포인트 사용, 쿠폰 사용, 송금, 재고 차감처럼 한 번만 발생해야 하는 비즈니스 이벤트에서 문제가 크다.

## 3. 멱등하지 않은 주문 생성 예시

아래 API가 있다고 가정한다.

```http
POST /orders
Content-Type: application/json

{
  "productId": 1,
  "quantity": 1
}
```

서버가 요청을 받을 때마다 단순히 주문 row를 insert하면, 같은 요청이 두 번 들어왔을 때 주문이 두 개 생성된다.

```text
1번째 요청 -> orders row 생성: orderId=100
2번째 요청 -> orders row 생성: orderId=101
```

사용자 입장에서는 한 번 주문했다고 생각하지만 서버 상태는 두 번 주문한 상태가 된다.

## 4. Idempotency-Key 방식

Idempotency-Key는 클라이언트가 하나의 비즈니스 작업을 식별하기 위해 서버에 전달하는 고유 키다.

```http
POST /orders
Idempotency-Key: 6f8d6f9a-2a11-4c8c-b70c-13e9a7e57c12
Content-Type: application/json

{
  "productId": 1,
  "quantity": 1
}
```

서버는 이 키를 저장하고 다음 규칙으로 처리한다.

- 처음 보는 key면 실제 비즈니스 로직을 실행한다.
- 이미 성공한 key면 비즈니스 로직을 다시 실행하지 않고 이전 응답을 반환한다.
- 같은 key인데 요청 내용이 다르면 잘못된 재사용으로 보고 에러를 반환한다.
- 같은 key가 아직 처리 중이면 충돌 또는 처리 중 상태를 반환한다.

핵심은 중복 요청을 막는 것이 아니라, 중복 요청이 와도 같은 결과로 수렴하게 만드는 것이다.

## 5. 서버 저장 모델

학습용으로는 다음과 같은 테이블을 둘 수 있다.

```text
idempotency_keys
- id
- idempotency_key
- user_id
- request_hash
- status
- response_code
- response_body
- created_at
- expires_at
```

`idempotency_key`만으로 유일성을 잡기보다 보통 `user_id + idempotency_key` 조합으로 잡는다. 서로 다른 사용자가 같은 key 값을 보내도 충돌하지 않아야 하기 때문이다.

`request_hash`는 같은 key로 다른 요청 body를 보내는 실수를 잡기 위해 사용한다.

## 6. 처리 흐름

```text
1. 요청에서 Idempotency-Key 헤더를 읽는다.
2. 사용자 식별자와 key로 기존 idempotency record를 조회한다.
3. record가 없으면 PROCESSING 상태로 먼저 저장한다.
4. 실제 비즈니스 로직을 실행한다.
5. 성공하면 응답 status와 body를 record에 저장하고 SUCCESS 상태로 바꾼다.
6. 같은 key로 다시 요청이 오면 저장된 응답을 그대로 반환한다.
```

중요한 점은 비즈니스 로직 실행 전에 key를 먼저 선점해야 한다는 것이다. 그래야 동시에 같은 요청이 들어와도 둘 다 주문을 생성하는 상황을 막을 수 있다.

## 7. 실습 순서

이 프로젝트에서는 다음 순서로 학습한다.

1. 멱등성 없는 `POST /orders` API를 만든다.
2. 같은 요청을 여러 번 보내 주문이 중복 생성되는 문제를 확인한다.
3. FE에서 버튼 더블클릭 또는 요청 재시도로 중복 요청 상황을 재현한다.
4. BE에 `Idempotency-Key` 저장 테이블과 처리 로직을 추가한다.
5. 같은 key로 재요청하면 주문이 추가 생성되지 않고 이전 응답이 반환되는지 확인한다.
6. 같은 key와 다른 요청 body 조합을 에러로 처리한다.
7. 동시에 같은 key 요청이 들어오는 경우에도 주문이 하나만 생성되는지 확인한다.

## 8. 구현 시 주의할 점

- key는 클라이언트가 요청 단위로 생성한다. 보통 UUID를 사용할 수 있다.
- 서버는 key를 영구 보관하지 않고 일정 시간이 지나면 만료시킬 수 있다.
- 같은 key의 응답을 재사용하려면 response code와 response body를 저장해야 한다.
- 외부 결제 API처럼 외부 시스템도 involved되는 경우, 외부 API의 idempotency 지원 여부도 확인해야 한다.
- DB unique constraint 없이 애플리케이션 코드만으로 중복을 막으려 하면 동시성 상황에서 깨질 수 있다.

## 9. 이 스터디의 목표

이 스터디에서는 중복 요청이 어떤 문제를 만들 수 있는지 재현하고, 이를 해결하기 위해 서버가 어떤 상태를 저장해야 하는지 살펴본다. 이후 동시성 상황에서도 안전하게 동작하도록 필요한 제약과 처리 흐름을 코드로 확인한다.
